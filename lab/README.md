# lab/ — наши расширения Open WebUI

Тулзы, функции и скрипты, которыми мы превращаем Open WebUI в кокпит LLM/RL-инженера:
подключаем свои чекпойнты, отлаживаем модель, смотрим роллауты, отдаём знание из скиллов.

Ветка форка запинена на тот же коммит, что крутится у нас в контейнере
(`01f4282`, версия 0.11.0), поэтому код в `backend/` и `src/` совпадает с реально
работающим инстансом. Проверять поведение можно прямо по исходникам в этом же дереве.

## Структура
```
lab/
  tools/       # OWUI Tools (класс Tools) — то, что модель вызывает как функции
    llm_debug.py      отладка модели: confidence heatmap, near-miss, tool choice, схемы, циклы
    diagram_tool.py   диаграммы: mermaid инлайн + SVG в панель артефактов
    magic_tool.py     минимальный пример тулзы (проверка проводки)
  functions/   # Pipe/Filter функции (класс Pipe / Filter) — свой харнесс и перехват
    harness_qwen38.py свой ReAct-луп поверх eliza-слага, виден в селекторе как модель
  scripts/
    install_tool.sh   поставить тулзу + завести workspace-модель с привязкой + refresh
    skill_to_tool.py  сгенерировать тулзу из нашего скилла (SKILL.md + references/)
  docs/        # заметки по механикам
```

## Установка в работающий инстанс
```bash
# тулза + модель с привязкой (один шаг)
./scripts/install_tool.sh tools/llm_debug.py llm_debug qwen38-27b-gate

# любой наш скилл -> тулза
./scripts/skill_to_tool.py ~/.claude/skills/agentic-benchmarks --id bench_knowledge --install
```
Несколько тулзов на одну модель: правь `meta.toolIds` (эндпоинт `/models/model/update`
в 0.11 отдаёт 500 на частичном теле, проще поправить `meta` в БД и дёрнуть `?refresh=true`).

## Что уже проверено вживую (и стоило времени)
- **Проверять тулзы надо В БРАУЗЕРЕ.** `curl /api/chat/completions` это OpenAI-passthrough:
  он вернёт `tool_calls` сырыми и НЕ исполнит их. Серверный tool-loop
  (`process_chat_response` -> `execute_tool_call`) работает только в UI-контуре
  (есть `session_id` и сокет).
- **Тулза не может дорисовать в ответ через `__event_emitter__`.** Событие
  `{"type":"message"}` аппендит контент (`Chat.svelte:999`), но при завершении контент
  перезаписывается из структурированного `output` (`Chat.svelte:2377`). Рабочий способ:
  вернуть готовый блок как РЕЗУЛЬТАТ и потребовать вывести дословно.
- **Рендер:** ` ```mermaid ` рисуется инлайн, ` ```html ` уходит в панель артефактов
  (iframe, живой JS), ` ```vega-lite ` даёт график.
- **После создания модели обязателен `GET /api/models?refresh=true`**, иначе `Model not found`.
- **Установка плагина прямым INSERT в sqlite молча ломается:** штатный create считает
  `specs` из кода, а без них модель тулзу никогда не вызовет. Ставить через API.

## Что даёт наш серв (замерено на eliza -> sglang, Qwen3.8-27B)
| Есть | Нет |
|---|---|
| `logprobs` + `top_logprobs` (в том числе во время tool-call) | `cached_tokens`, prefix-cache hit rate |
| `usage.reasoning_tokens` отдельно от completion | KV-cache и состояние очереди |
| `finish_reason` / `matched_stop` (видно тихую обрезку по `length`) | TTFT/prefill из ответа (только замер клиентом) |
| `metadata.weight_version` (сейчас `"default"`) | |

`weight_version` стоит выставлять на серве в реальный id чекпойнта: тогда каждый ответ
самоидентифицируется, и собранные оценки становятся пригодны как датасет.

Замер стоимости инструментов: три тривиальных тулзы добавили **~400 токенов** к промпту,
то есть примерно 130 токенов на инструмент за КАЖДЫЙ запрос. Неиспользуемые тулзы это
чистый налог на контекст, `inspect_tool_choice` его показывает.

## llm_debug: что показывает
- `inspect_confidence(prompt)` — ответ, раскрашенный по уверенности токенов, средняя
  уверенность, число неуверенных мест, флаг обрезки, и таблица «почти выбрал другое»
  (где отрыв лидера от второго кандидата меньше 1.2 логпроба).
- `inspect_tool_choice(prompt, tools_json)` — какой инструмент позван и с какой
  уверенностью на токенах имени, что почти позвал вместо, валидация аргументов против
  JSON-схемы (пропущенные обязательные, лишние поля, невалидный JSON, несуществующее имя),
  стоимость схем в токенах, список неиспользованных тулзов, флаг протечки XML мимо парсера.
- `detect_tool_loops(trace_json)` — повторные вызовы с теми же аргументами и пинг-понг
  между двумя инструментами.

## Урок про доставку отчётов (стоил двух итераций)
1. **HTML-артефакт на 17 КБ не доезжает.** Модель упирается в `max_tokens`, копируя его
   дословно, блок ` ```html ` не закрывается, артефакт не рендерится. Проверено в браузере.
2. **Компактный markdown + ` ```vega-lite ` (около 1 КБ) доезжает всегда** и рисуется
   графиком нативно. Это и есть правильный примитив для отчётов тулзы.
3. **Модель вправе НЕ выполнять инструкции из тела результата тулзы.** В проверке Qwen
   воспроизвёл отчёт, но приписал: «указания из тела инструмента выполнять не буду».
   Это корректная гигиена против prompt injection, и на неё нельзя закладываться.
   Надёжная доставка это outlet-фильтр, который дописывает отчёт после генерации, либо
   просьба со стороны пользователя или системного промпта.

## Что проверено про фильтры (outlet)
- **`self.toggle = True` превращает фильтр в РУЧНУЮ кнопку.** В `resolve_filter_pipeline`
  (`utils/filter.py`) ветка `if getattr(function_module, 'toggle', None): return filter_id
  in enabled_filter_ids`. Глобальный фильтр с `toggle` НЕ применяется, пока пользователь
  не нажмёт кнопку в конкретном чате. Для «всегда работает» атрибут не ставить.
- **`/functions/id/<id>/toggle` и `/toggle/global` это ПЕРЕКЛЮЧАТЕЛИ, не «включить».**
  Повторный запуск установщика выключил бы функцию. `install_function.sh` сверяет
  текущее состояние в БД и дёргает ручку только при расхождении.
- **Из outlet персистится ТОЛЬКО `content`.** Правки `msg["meta"]` и `msg["usage"]` в БД
  не доезжают (проверено: остаются null). Поэтому провенанс несёт машиночитаемый футер
  в content: он же попадает в `snapshot.chat` при выгрузке feedback.
- **`params` модели фильтру не видны:** в `__model__["info"]` есть `base_model_id` и `meta`,
  но нет `params` (то же в ответе `/api/models`). Читаем их из таблицы `model` напрямую.
- Фильтр применяется в UI-контуре; через `POST /api/chat/completions` (passthrough) он не
  срабатывает, как и серверный tool-loop.

## Импорт роллаутов (`scripts/import_rollout.py`)
JSONL с траекториями превращается в чаты: `[FAIL] i0 · r=0.0` в заголовке, сворачиваемые
тул-вызовы с аргументами и результатами, теги `outcome:fail` / `reward:zero`, папка на прогон
и футер с trace_id, reward, target и outcome. Проверено на реальных booking-трейсах
(`step-attribution-model/data/real_sample_v1.jsonl`): 20 сообщений, 31 output-элемент,
тул-вызовы отрисовались, ни один не завис в "Executing".

Понимает два формата: наш step-attribution (`history` со `step_idx`/`type`/`content_short`/
`tool_name`/`tool_args`) и обычный OpenAI (`messages` с `tool_calls`/`tool_call_id`).

```bash
./scripts/import_rollout.py traces.jsonl --limit 5 --folder "rollouts/tau2" --tag rl-v7
./scripts/import_rollout.py traces.jsonl --limit 1 --dry-run     # только разбор, без записи
```
Ключевое требование формата: вся цепочка ОДНОГО хода (мысли, вызовы, результаты, финальный
текст) кладётся в ОДНО assistant-сообщение плоским списком `output`, потому что фронт матчит
`function_call_output` с `function_call` по `call_id` внутри одного сообщения. Разложишь по
разным сообщениям - вызовы навсегда останутся в "Executing...".

Дальше поверх импортированного трейса работает всё остальное: оценки (и они попадут в выгрузку
feedback), теги, а также контрфактический реплей - правишь результат тула и жмёшь regenerate,
ветки видны переключателем.

## Длинные ответы и code-generation (реальный баг с демо)
Симптом: на задаче «напиши прототип графового FSM-харнесса» ответ рвался посреди кода без
всякого предупреждения. Диагноз по API: `finish_reason=length`, `completion_tokens` РОВНО равны
лимиту. Причина глубже лимита: reasoning-модель без парсера пишет рассуждения прямо в ответ и
проедает бюджет.

Три фикса, все проверены:
1. **`max_tokens` 4096 → 16384** в пресетах реестра.
2. **Системный промпт «не рассуждай вслух»** в `defaults.params.system`. Замер на том же
   запросе: было обрезание на 16384, стало `finish_reason=stop` и 6778 токенов, ответ целый.
   Это не косметика, а именно устранение причины.
3. **Фильтр `run_metadata` больше не даёт тихой обрезки:** закрывает незакрытый ```-фенс (иначе
   ломается разметка всего сообщения), пишет предупреждение и ставит `truncated=1` в футер.

Плюс `functions/autocontinue.py` - Pipe-«модель» без потолка длины: если генерация упёрлась в
лимит, харнесс сам просит продолжить с места обрыва и склеивает куски. Проверено с
`CHUNK_TOKENS=1500`: 4 части, 23 317 символов, фенсы сбалансированы, в конце пометка о склейке.
Честное ограничение: суммарно всё равно нужно влезть в окно контекста.

И `functions/inspect_actions.py` - кнопки под ответом (Actions): raw (исходный текст),
expand (обрезан ли ответ и как продолжить), provenance (каким слагом и с какими параметрами
сгенерировано), stats (символы, доля кода, число блоков, флаг обрезки).

## 🚨 Грабля инфраструктуры: удалённый WAL у работающего контейнера
На демо-VM обнаружено: процесс приложения держит `webui.db-wal` и `webui.db-shm` в состоянии
**(deleted)**. Последствия:
- API отдаёт полные данные (читает через свои соединения), а любой ВНЕШНИЙ читатель того же
  файла видит только старый чекпойнт. Отсюда «функция создана, но её нет в БД»;
- всё, что записано после удаления WAL, живёт только в удалённом иноде и пропадёт при
  перезапуске контейнера;
- починить на месте нельзя: `PRAGMA wal_checkpoint(TRUNCATE)` падает с `disk I/O error`,
  потому что shm-сегмент тоже удалён.

Отсюда правила:
- **никогда не трогать каталог данных работающего контейнера снаружи** (tar/rm/cp в примонтированный
  volume). Именно так теряется WAL;
- **скрипты должны читать и писать через API, а не напрямую в sqlite.** Прямая запись в БД
  вдобавок рискует быть невидимой для приложения или затёртой;
- перед любым перезапуском снимать бэкап через API: `chats/all/db`, `functions/export`,
  `configs/export`, `models/export`, `tools/export` (см. `.backups/`).

## Почему UI тормозит на длинных ответах (разбор по коду)
Главная причина не в подсветке кода, а в объёме, который прилетает по сокету.
`middleware.py:4094` `full_output()` возвращает ВЕСЬ накопленный вывод, и он кладётся в
КАЖДУЮ дельту (`middleware.py:4797-4801`). Размер батча регулирует
`CHAT_RESPONSE_STREAM_DELTA_CHUNK_SIZE`, дефолт которого **1** (`env.py:996`), то есть один
`sio.emit` на токен. Трафик и число `JSON.parse` на главном потоке растут КВАДРАТИЧНО от длины
ответа: для 16384 токенов это порядка сотен мегабайт за одну генерацию. Отсюда и наблюдение
«на 4096 терпимо, на 16384 всё встаёт»: рост не линейный.

Смягчение без перезапуска контейнера: `stream_delta_chunk_size` это псевдо-параметр Open WebUI
(`payload.py:93`), его можно задать в params пресета, что реестр и делает (50). Важно: env
работает ПОЛОМ (`max(ENV, params)`), поэтому параметр модели может только поднять батч.

Усилители из того же разбора:
- `CodeBlock.svelte:566-568` подсвечивает весь блок через `{@html}` без мемоизации и без гейта
  по `done`; замер: 60k кода это 228 КБ HTML и ~9k DOM-узлов, которые пересоздаются каждый кадр;
- незакрытый ``` делает весь хвост ОДНИМ code-токеном, поэтому «большой код» бьёт больнее всего
  (наш фильтр теперь закрывает фенс, это заодно и мера производительности);
- `Chat.svelte:2102-2132` автопрокрутка делает три чтения `scrollHeight` в трёх кадрах, каждое
  это принудительный layout контейнера с `content-visibility: auto`;
- `Chat.svelte:950` и `:2483` печатают полный объект дельты в консоль на каждый чанк.

Поправка к нашим прежним предположениям: `AIOHTTP_CLIENT_TIMEOUT` по умолчанию **None**, а не 300
(`env.py:574-578`, 300 стоит только в ветке исключения). У нас он не выставлен, так что таймаут
к обрывам отношения не имеет. Но если его выставить, он `total` на весь стрим, и при срабатывании
в БД останется только `error`, потому что `ENABLE_REALTIME_CHAT_SAVE=False` и `done` не доедет.

Честно про измерение: подтвердить выигрыш от батчинга в автоматизированном браузере НЕ удалось.
Фоновая вкладка троттлит rAF до 1 Гц и не отдаёт longtask-события, то есть тормоза рендера там
физически не воспроизводятся. Фикс обоснован кодом и безопасен, но проверять его надо руками в
обычном браузере.

## Выгрузка feedback -> DPO (`scripts/export_feedback.py`)
Собирает пары chosen/rejected по общему `parentId` с противоположными рейтингами и печатает
ЧЕСТНУЮ диагностику: сколько пар, сколько разметчиков, разнообразие промптов, есть ли провенанс.
`--stats` только диагностика, `--out dpo.jsonl` пишет пары, `--min-pairs N` не пишет, если мало.

Проверено на живом фидбеке (один реальный дизлайк с комментарием). По ходу вскрылась и исправлена
настоящая грабля формата:
- **`snapshot.chat` это ЦЕЛАЯ строка ChatModel** (id/user_id/title/chat/...), а реальный диалог
  лежит в `snapshot.chat.chat.history.messages`, на уровень глубже. Прежний путь
  `snapshot.chat.history` пустой. `_history()` берёт вложенный chat с фолбэком.

Практический вывод (совпал с ревью): **DPO-пары из OWUI редки по устройству.** Пара образуется
только когда под одним `parentId` есть два ответа и оба размечены с ПРОТИВОПОЛОЖНЫМ рейтингом.
Обычный regenerate тут не помог: он не оставил размеченного сиблинга, а снапшот, похоже, сериализует
только активную ветку. Значит для сбора пар нужен арена/side-by-side режим (`sibling_model_ids`
проставляется автоматически), а не ручные лайки на одиночных ответах. Как очередь на разбор багов
поток полезен и без пар.

## Починка безопасности + удалённого WAL демо-VM (`scripts/secure_relaunch.sh`)
Готовый к запуску скрипт для окна обслуживания. НЕ запускается сам без трёх решений (они не мои):
точный `CORS_ORIGIN`, сервисный `SERVICE_TOKEN` вместо личного, способ auth (trusted-header за
прокси или OIDC). Guard проверено: без них останавливается ДО любого действия.

Порядок: (1) свежий бэкап через API (читает живые данные, не трогает отвязанный WAL); (2) новый
контейнер с включённым auth, закрытым CORS, secure-cookie, на ЧИСТОМ томе (старый сохраняется как
`-old`); (3) восстановление чатов/функций/конфига из бэкапа; (4) проверка периметра той же
curl-цепочкой, что вскрыла дыры (signin без пароля → 401, Origin не отражается). Личный eliza-токен
после этого отозвать. Бэкапы в `.backups/`.

## Слепая арена для DPO-пар (`scripts/setup_arena.py`)
Закрывает главный пробел выгрузки feedback: одиночные лайки почти не дают пар. Арена-модель на
каждый запрос СЛУЧАЙНО выбирает одну из под-моделей (слепо), а feedback штатно получает
`sibling_model_ids` и реальный `selected_model_id` — то есть голос сразу образует пару под одним
промптом. Плюс лидерборд Elo.
```bash
./setup_arena.py --models ab-base,ab-rl-v7 --name "Checkpoint Arena" --id ckpt-arena
./setup_arena.py --list
```
Проверено: арена `ckpt-arena` появляется в селекторе, сравнивает base и RL v7. Поток: выбрать её
в чате → задать вопрос → проголосовать → `./export_feedback.py --out dpo.jsonl` собирает пары.
Механика по коду: выбор под-модели `middleware.py:2261` (random.choice), конфиг
`POST /api/v1/evaluations/config` (`evaluation.arena.models`).

## Обновить демо одной командой (`scripts/provision.sh`)
Ставит ВЕСЬ кокпит (функции, тулзы, модели, арену) на работающий контейнер через API. НЕ
пересоздаёт контейнер и НЕ трогает веса (eliza-сервы на GPU живут отдельно).
```bash
# локально
./scripts/provision.sh
# на VM-демо
ssh <vm> 'cd ~/lab && PATH=$HOME/bin:$PATH ./scripts/provision.sh'
```
Идемпотентно, повторный запуск обновляет уже стоящее. Пересоздание контейнера НЕ нужно для
обновления — оно потребовалось ровно один раз, чтобы починить отвязанный WAL (из-за него ранние
апдейты не персистились). После чистого тома апдейт = только этот скрипт.

## Фейловер между слагами (P0 из ROADMAP)
Наши сервы преемптятся ПО ОДНОМУ: реальная ночная ситуация — `qwen38-27b-gate` лежит,
`qwen35-v7-gate` работает. Раньше все тулзы и пайпы были прибиты к qwen38, поэтому весь кокпит
выглядел сломанным при живой второй модели.

Теперь `llm_debug`, `autocontinue` и `project_gen` резолвят **первый живой слаг** (предпочтение
из valves, дальше кандидаты; кэш 90 с, чтобы не долбить `/models`), а при полном отсутствии
живых сервов возвращают человеческое объяснение и отсылку к модели **Serve Status**.

Проверено ровно в этих условиях: qwen38 = 400, v7 = 200 → резолвер выбрал `qwen35-v7-gate`,
отчёт построился. Отдельно исправлено враньё в шапке: отчёт печатал слаг из настроек, а не тот,
что реально ответил (`_lab_slug` из ответа).

## Экспорт диалога (`functions/chat_export.py`)
Две кнопки под ответом: **Markdown** (в тикет/отчёт) и **JSONL** (в датасет, формат OpenAI
`messages`). Файл создаёт сервер через Files API, модель ничего не копирует.
Из выгрузки вырезаются футер провенанса и протёкшее `<think>`, tool-вызовы разворачиваются в
`[tool call] name(args)` / `[tool result] ...`.
Проверено в браузере: кнопка Export → файл `chat-*.md` (HTTP 200, `text/markdown`), структура с
заголовками ролей и моделью.

## GPU и пул в чате (`functions/gpu_status.py`)
Модель **GPU Status** в селекторе: гарантия пула, использование, спрос, число операций, и вывод
о том, почему нас вытесняет (fair-share внутри пула, а не размер серва: наши 1 и 2 GPU). Ходит в
YT, а не в модель, поэтому доступна, когда все чекпойнты лежат.
Проверено на живом YT: 120/128 GPU, 9 операций, очередь распознана. Где нет `ya`/VPN (корп-VM)
вернёт понятное сообщение вместо падения.

## Бюджет контекста (`tools/context_budget.py`)
Показывает, из чего складывается промпт: служебная обвязка, системный промпт, СХЕМЫ ИНСТРУМЕНТОВ,
история, текущий текст. Меряет разностью реальных `prompt_tokens` (по 1 дешёвому вызову на часть),
а не эвристикой «символы/4», которая на кириллице врёт в разы.

Первый же замер показателен: 2 тривиальных инструмента = **312 токенов (75% промпта), ~156 на
инструмент**, при том что сам вопрос стоил 17. Неиспользуемые тулзы это постоянный налог на
каждый запрос, и теперь его видно.
